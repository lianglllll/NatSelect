# 代码四维审查门禁

本规则确保 **每次代码变更后必须通过四维审查**，任何维度出现 🔴 严重问题时必须修复后才能交付。

---

## 适用范围

本规则适用于 NatSelect 项目中所有代码变更，包括但不限于：
- NatSelect/ 引擎核心代码
- NatSelectDemo/ 演示代码
- .proto 协议文件
- 配置文件（.yaml、.csproj）

---

## 🔍 四维审查标准

### 维度1：正确性 ✅

每段代码变更必须确认：

1. **逻辑无误**：业务逻辑按需求正确实现
2. **边界安全**：
   - `null` 引用已检查（使用 `?.`、`??` 或显式判空）
   - 集合操作已判空（`?.Count > 0` 或 `Any()`）
   - 数值范围已验证（非负、非零等）
3. **并发安全**：
   - Actor 邮箱内的操作是线程安全的（单线程调度保证）
   - 跨 Actor 共享状态有适当的同步机制
   - `lock`/`Interlocked` 使用正确
4. **异常处理**：
   - 关键路径有 try-catch
   - 异常信息足够诊断问题
   - 资源在 finally/DisposeAsync 中释放
5. **资源管理**：
   - `DataStream` 使用后归还池（`Dispose()`）
   - `IAsyncDisposable`/`IDisposable` 正确实现

### 维度2：安全性 🔒

1. **输入校验**：
   - 所有客户端输入必须校验（长度、范围、格式）
   - Proto 反序列化后验证关键字段
2. **敏感信息**：
   - 无硬编码密钥、Token、密码
   - 日志不输出敏感数据
3. **网络安全**：
   - 消息 `Sender` 来源可信性考虑
   - 连接建立时有基本的合法性检查

### 维度3：性能 ⚡

1. **对象分配**：
   - 热路径避免不必要的 `new`
   - 优先使用 `DataStream` 池化机制
   - 大对象考虑 `ArrayPool<T>`
2. **Actor 设计**：
   - `mailboxCapacity` 合理（默认 1024，高吞吐可适当增大）
   - 消息处理不过度阻塞
3. **定时器**：
   - 频率合理（不创建过高频率定时器）
   - 随 Actor 生命周期自动清理
4. **内存**：
   - 事件订阅在适当时机取消（避免泄漏）
   - 配置变更回调及时注销

### 维度4：可维护性 📖

1. **命名**：类/方法/变量名清晰表达意图
2. **结构**：
   - 方法不超过 40 行
   - 类职责单一
3. **规范**：
   - 命名空间匹配目录结构 (`NatSelect.Core`、`NatSelect.Network` 等)
   - Actor 构造第一个参数是 `ActorContext`
   - Proto partial class 有 `[ProtoId]` 标注
4. **注释**：
   - 复杂逻辑有解释
   - 公开 API 有 XML 文档注释

---

## 🔄 审查流程

```
代码变更完成
    ↓
逐文件走四维检查清单
    ↓
发现 🔴 严重问题 → 立即修复 → 重新检查
    ↓
全部 🟢 或仅有 🟡 建议 → 审查通过
```

---

## 🚦 判定标准

| 级别 | 含义 | 行动 |
|:---:|------|------|
| 🔴 严重 | 影响正确性、安全性或导致明显性能问题 | **必须立即修复** |
| 🟡 建议 | 有改进空间但不阻塞 | 评估后决定是否修复 |
| 🟢 优秀 | 符合最佳实践 | 无需行动 |

**门禁规则**：存在任何 🔴 问题时，代码不得交付/合并。

---

## 📋 检查清单快查

每次代码变更后逐项确认：

```
□ 1. 空引用是否全部处理？
□ 2. 异常路径是否覆盖？
□ 3. 资源是否正确释放？
□ 4. 输入是否经过校验？
□ 5. 是否有硬编码敏感信息？
□ 6. 热路径是否有不必要的分配？
□ 7. 方法是否过长（>40行）？
□ 8. 命名空间是否匹配目录？
□ 9. 命名是否清晰表达意图？
□ 10. 复杂逻辑是否有注释？
```
